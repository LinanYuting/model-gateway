## 1. 免费通道依赖第三方，稳定性不可控

### 影响

免费通道的上游是 **OFM 独立服务**（`OFM_ENDPOINT`，默认 `http://localhost:18900`），它是整个网关唯一「不需要任何密钥就能用」的出口。它的可用性直接决定三件事：

1. **免费通道本身**是否可用；
2. **fallback 链路**是否成立——主通道（sponsored/aiping）失败时会尝试 free 兜底，free 也挂就没有第二层了，直接 500；
3. **阶段 3 联调**时其它组的测试是否跑得起来——组员2 的大量用例、组员3 的看板数据都依赖有流量能打通。

影响面不是「某条通道慢」，而是**兜底能力归零**。

**实测佐证**：OFM 未启动时，一次普通请求的结果是

```
HTTP/1.1 500 Internal Server Error
{"error":"Internal Server Error","message":"Free channel forward failed: connect ECONNREFUSED ::1:18900; ..."}
```

连续 3 次后通道被熔断，再请求变成 503 `{"error":"Service Unavailable","message":"No available channel"}`——此时**整个网关对外不可用**，不只是免费通道不可用。

### 概率

**高，且已经在发生。** 理由是它依赖的不是一个托管服务，而是每台机器上各自克隆、各自启动的本地进程：

- 本机实测期间 OFM 从未启动（未安装），免费通道的 `healthStatus` 一直是 `unhealthy`；
- 只要有人忘了先起 18900，或被 IDE 重启杀掉，免费通道即刻失效；
- OFM 仓库本身在演进（`packages/standalone/cli.mjs`），上游行为变化会直接传导进来。

### 缓解措施

| 措施 | 现状 | 说明 |
|---|---|---|
| 健康探测 | ✅ 已实现 | `src/services/backup.js` 的 `startHealthProbe`，探测结果写入 `channels.healthStatus`，`unconfigured` 与 `unhealthy` 区分开了 |
| 熔断隔离 | ✅ 已实现 | 连续失败 ≥ 3 次 → 移出候选池，冷却 60s 后自动重试（`src/services/circuitBreaker.js`）。实测 `failureCount=3` 后路由确实绕开 free |
| 限流保护 | ✅ 已实现 | `FREE_CHANNEL_RPM`（默认 30/分钟）进程内滑动窗口，实测 `RPM=2` 时第 3 次返回 429 + `Retry-After: 60`。**这是保护上游的，不是保护自己的** |
| 启动顺序 | ⚠️ 靠文档 | 必须「先 OFM 18900，后网关」，见 `docs/deployment.md` §6。没有自动化校验 |
| 备用通道 | ❌ 未就绪 | sponsored / aiping 端点本期留空（aiping 明确延后），free 挂了没有同级别替代 |

**建议补的两件事**：

1. 网关启动时若 `OFM_ENDPOINT` 探不通，**在日志里打一行显眼的警告**并写入一条 `critical` 告警，而不是静默把 `healthStatus` 设成 `unhealthy` 就完事。现在这个信号只在看板上，不进日志，起服务的人看不到。
2. 阶段 3 联调前，把「先起 18900」写进联调 checklist，并且用一条 `curl /v1/models` 作为放行条件，而不是靠口头提醒。

## 2. 仅限社团内部使用，禁止对外提供服务

### 影响

这不只是「合规口径」问题，它同时是前一条风险的放大器。一旦对外：

- **第三方上游会被打穿**。免费通道限流是**进程内**的（`src/services/rateLimiter.js` 用内存 `Map`），单机多进程或横向扩容后限流各算各的，`FREE_CHANNEL_RPM` 形同虚设，30/分钟会被瞬间放大成 N×30。
- **密钥与令牌暴露面从「本机」变成「公网」**。§3 详述的明文存储问题，在内网是「熟人社会」，在公网就是直接可利用。
- **没有 SLA 可承诺**。OFM 挂掉网关就 500/503（§1 实测），没有任何对外服务该有的降级话术。
- **可能违反 OFM 上游条款**。免费模型的额度是按人给的，代理转发给外部用户属于二次分发，上游有权随时切断。

### 概率

**由部署方式决定，不设上限就是 100%。** 当前代码没有任何「只能本机访问」的硬约束：`app.listen(PORT)`（`src/server.js:46`）监听全部网卡，不是 `127.0.0.1`。同一局域网内任何人都能直接访问 `/api/admin/*`（若 `ADMIN_TOKEN` 为空则无需任何凭证）。

### 缓解措施

| 措施 | 现状 | 说明 |
|---|---|---|
| 绑定回环地址 | ❌ 未做 | `app.listen(PORT)` 默认 `0.0.0.0`。改成 `app.listen(PORT, '127.0.0.1')` 即可挡住局域网，一行改动 |
| `ADMIN_TOKEN` 必设 | ⚠️ 靠自觉 | 留空时 `/api/admin/*` **完全开放**，含明文令牌列表。`.env.example` 默认是空 |
| 不做公网部署 | ✅ 约定 | 本文与 `deployment.md` 均明示仅限内部 |
| 使用范围告知 | ✅ 本文 | 见下方红线 |

**红线（请写进阶段 3 联调通知里）**：

> 本网关及其背后的免费模型通道**仅供社团内部成员在学习、测试、演示场景使用**。
> 不得部署到公网、不得以任何形式向社团外提供调用服务、不得用于商业用途或二次分发。
> 违反上述约定的全部后果由部署者承担，与项目组及上游模型提供方无关。

**建议补的一件事**：把 `ADMIN_TOKEN` 改为**启动时强制校验**——为空就拒绝启动并提示「请先设置 ADMIN_TOKEN」。现在「留空=开放」这个设计是为了本机开发方便，但它同时也是最容易被带进演示环境的一个坑。至少应该在启动日志里打一行 `[WARN] ADMIN_TOKEN 未设置，管理接口对外开放`。

## 3. 密钥现状：1.3 完成前全部明文存储

### 影响

当前有三处明文，风险等级递增：

| 位置 | 内容 | 暴露面 |
|---|---|---|
| `channels.config_json` | `apiKey` / `apiKeys[]` 明文落库 | 拿到 `data/*.db` 文件 = 拿到全部上游密钥 |
| `GET /api/admin/channels` | 直接返回解析后的 `config`，含 `apiKey` | 管理接口被越权 = 密钥泄露 |
| `GET /api/admin/tokens` | 返回明文 `token` 字段 | 管理接口被越权 = **所有项目**的业务令牌泄露 |

**实测佐证**：`GET /api/admin/tokens` 的原样返回（`docs/api.md` §3.3）里 `"token":"78770f03-..."` 就是明文。同一次实测里 `GET /api/admin/channels` 也把 `config.apiKey` 原样吐了出来。

第三行的影响最大：业务令牌泄露不只是「别人能用你的额度」，而是**所有用量都会记在原项目名下**，配额告警与 `call_logs` 全部失真，事后无法区分是谁在调用。

### 概率

**只要满足「数据库文件外流」或「管理接口被越权」任一条件就是 100%。** 而这两条在当前状态下都不难达成：

- `data/` 已在 `.gitignore` 里 ✅，但**备份产物**（`src/services/backup.js` 的定时备份）仍落在本机磁盘，拷走即可；
- 管理接口在 `ADMIN_TOKEN` 为空时无需凭证（见 §2）。

### 缓解措施

| 措施 | 现状 | 说明 |
|---|---|---|
| `.env` 与 `data/` 不入库 | ✅ 已生效 | `.gitignore` 覆盖；实测 `git status` 无这两项 |
| `ADMIN_TOKEN` 守护 | ✅ 已实现 | 设置后 `/api/admin/*` 需 `x-admin-token`，401 结构合规（实测） |
| 密钥加密落库（组员1 的 1.3） | ❌ 未完成 | 任务书要求先提交约 200 字设计说明经组长评审再实施 |
| 备份文件保护 | ⚠️ 未评估 | 备份目录权限未核查，落在项目目录内 |
| 令牌回显脱敏 | ❌ 未做 | `GET /tokens` 建议只回显前后各 4 位，或加 `?reveal=1` 才给全量 |

**过渡期的三条硬规矩**（写在 1.3 交付之前）：

1. 演示环境**必须**设 `ADMIN_TOKEN`，且不能用 `demo` / `admin` 这类弱口令；
2. 任何人贴日志、截图、提 issue 时，**先过滤掉 `token` 与 `apiKey` 字段**——这份文档里的示例值都是本机临时令牌，已随环境重建失效；
3. `data/*.db` 及备份**不得**通过微信/QQ/邮件传输。要复现别人的数据，用脚本重新造，别传库文件。

**建议**：1.3 的设计说明里应明确「存量数据的迁移路径」——旧明文 key 要么在启动时一次性加密，要么保留明文但标记 `legacy` 并在读取时自动升级。后者更稳，不会因为加密方案上线导致存量通道全部失效。这一点任务书已经点到了，实施时别省。

## 4. Jev 开启会引入额外一次模型调用的延迟与开销

### 影响

Jev 的定位是「用一个小模型分析请求内容，建议走哪条通道」。开启后**每次请求**都会多一跳：

- **延迟**：多一次 LLM 往返。哪怕小模型很快，也是几百毫秒量级，而网关主链路的其它环节（路由、限流、日志）都是亚毫秒。也就是说 Jev 会把 P50 延迟提高一个数量级。
- **开销**：多消耗一次上游额度。如果这条「分析请求」也走免费通道，它会**占用 `FREE_CHANNEL_RPM` 的配额**——即一个用户请求消耗两个名额，实际可用请求数直接腰斩。
- **新的故障点**：Jev 调用本身可能超时或报错，必须保证它失败时**不阻断**主请求。

### 概率

**只要 `USE_JEV=true`，就是每次请求 100%。** 关闭时为零。

### 缓解措施

| 措施 | 现状 | 说明 |
|---|---|---|
| 总开关默认关闭 | ✅ 已实现 | `.env` 与 `.env.example` 都是 `USE_JEV=false` |
| 置信度阈值回退 | ✅ 契约已定 | `confidence < 0.6` 必须忽略 Jev 结论、回退规则路由并记 `decision="rule-default"`（契约 §1） |
| 调用失败不阻断 | ⚠️ 待验证 | 契约 §5 有要求，但 Jev 实现尚未接入（`router.js` 里 `JevRoute` 返回 `null` 的空壳），无法验证 |
| 关闭后零开销 | ✅ 已实现 | 关闭时 `routeRequest` 不进 Jev 分支，无额外调用 |
| 阈值可调 | ✅ 已实现 | `QUOTA_WARN_PERCENT` 同款模式 |

**三个必须注意的实现细节**（不是风险本身，但会让人误判风险）：

1. **`USE_JEV` 是模块级常量，改完必须重启**。`src/routes/router.js:5` 是 `const USE_JEV = process.env.USE_JEV === 'true'`，在模块加载时求值一次。改了 `.env` 不重启进程，开关不生效——如果联调时有人反馈「开了没反应」，先查这个，别去翻代码逻辑。
2. **`useJev` 参数在代理层被硬编码为 `false`**。`src/routes/proxy.js:55` 是 `useJev: false`，所以**只能靠环境变量开关**，不能按请求单独控制。如果后续要做「只对某类请求开 Jev」，这里得改。
3. **Jev 的调用不该挤占免费通道限流**。建议它的上游独立配置（不共用 `FREE_CHANNEL_RPM`），否则 §4 开头说的「名额腰斩」会真的发生，且很难归因。

**建议的验收口径**：1.4 合并后，用同一批请求分别在 `USE_JEV=true/false` 下跑，记录 P50/P95 延迟与 `X-Total-Tokens` 总量，把两组数字贴进 PR。没有这组数字，「延迟可接受」就是一句主观判断。

## 5. 顺带发现（超出 4.3 四项，但不写下来会漏）

这几条在写接口文档时实测出来的，属「文档与实现不一致」，不是运行期风险，但会在阶段 3 造成误会，一并列在这里，详情见 `docs/api.md` §8：

| # | 现象 | 会怎么坑人 |
|---|---|---|
| 1 | `/v1` 的 401/500 返回 `{"error":"字符串"}`，无 `error.type` | 客户端按契约写分支判断会全部落空 |
| 2 | 通道全熔断时返回 **503**，契约状态码表里没有 | 未处理分支，前端可能白屏 |
| 3 | `GET /circuit-breaker/:id` 字段名与契约不同（`isOpen` vs `open`） | 组员3 的熔断状态展示全空 |
| 4 | fallback 一次调用写**两条** `call_logs`，`totalRequests` 虚高 | 看板数字与真实调用数对不上，验收时会被当成 bug |
| 5 | `GET /tokens` 驼峰、`POST /tokens` 下划线 | 前端要写两套映射 |

这五条的修法在 `docs/api.md` §8 里逐条给了建议，**均需组长裁决**，本文不擅自改代码。
